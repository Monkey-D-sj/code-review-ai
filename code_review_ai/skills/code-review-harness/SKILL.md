# 评审过程纪律

本 skill 只管三件事：**在哪里取证**、**什么时候停止检索**、**什么时候交卷**。
「一个改动是不是回归」怎么判断，由 methodology 与语言 skill 负责，本 skill 不重复。

评审 loop 有轮数上限，且不保证跑得满：**在外面多待一轮，就少一次交卷的机会。**

## 一、现场是本次改动涉及的模块

现场 = 本次 diff 触碰的文件，加上它们**直接相邻**的落点。默认只在这个范围内活动。

| 读 | 说明 |
|---|---|
| 改动文件本身 | 整读，包括改动行以外的部分 |
| 同目录的相邻模块 | 模型 / Schema / 序列化边界，与改动文件成对出现的那一半 |
| 一跳调用关系 | 用 `get_impact` 拿改动符号的直接调用方与被调方，不靠翻目录猜 |

| 不读 | 说明 |
|---|---|
| SQL 种子、迁移、日志、模板、静态资源、配置 | 它们几乎从不持有本次改动的契约落点 |
| 其他业务模块 | 除非命中第二节的三种情况 |

契约的另一头通常在**同一层的平行实现**里——入参 Schema、出参 Schema、字段映射表、手写同步赋值、查询构造；不在下游的数据文件里。

## 二、只有三种情况允许离开现场

1. **落点本身就在那边**：你找到的契约另一头在模块外——那是现场，直接去。
2. **模块内的证据不足以判断调用方会不会坏**，而那个调用方在模块外——去读那个调用方。
3. **有指名道姓的反证需要核实**：某处显式做了兼容处理——只读那一处，读完立刻回来。

这三种之外，「出去找旁证证明自己那个判断成立」是不允许的：旁证成立与否，都不改变你已经读到的代码。

## 三、什么时候可以交卷

**能写出「哪个符号、哪一行、因为什么机制会坏」，就可以交卷。**

- 不需要先证明它一定会发生；不需要把所有落点找齐。
- 一条 finding 也可以先交，不要为了「一次交全」继续找。
- 每次工具调用之后问一次：**我现在能不能交卷？** 能，就交。

## 四、「绝不猜测」不等于「证据不全就不报」

- **猜测**：没读到代码就断言——禁止。
- **推断**：读到了代码，只是没有运行时证据——**可以报**，在 description 里写清依据与不确定处。

证据不足的正确动作是**少报并说清依据**，不是继续找。把不确定写出来，比不报有用。

## 五、交卷纪律

- 评审**只能**通过调用 `finish_review` 结束；自由格式的报告不算交卷。
- 确实没有具体回归就提交空 findings——那是一个有效结论，不是失败。
- 结束前不要整理长篇过程说明；findings 本身就是交付物。
